# Windows 11 backend design

Target: native Rust application, `x86_64-pc-windows-gnu`; Windows 11 x64. Design only: no code, hardware access, builds, tests, driver installs, or Windows runtime probes performed here.

Evidence labels: **O** observed source/artifact; **L** existing Linux hardware observation supplied by parent; **D** documented platform/project contract; **I** proposed implementation; **U** unresolved Windows/device behavior. Static decompilation is not a Windows execution trace. Current `README.md`, `replacement-plan.md`, and `src/` supersede older “not yet live” statements in protocol specifications.

Preserve existing public operations: `receiver::Receiver::{open,input,pad,read_profiles,write_profiles,read_version,enter_xbox_mode}`, `att::Connection::{open,read_profiles,write_profiles,enable_physical,next_physical,close}`, `gip::Gip` transactions/calibration, `input::{devices,run,run_receiver,run_wired}`, `Mapper`, and `profiles::{matching_rule,select,Debounce,Store}`. Replace OS I/O, not protocol/profile semantics. Keep byte-exact profile CRC/read-back checks, application acknowledgments, cancellation cleanup, layer/toggle/turbo behavior, and one selected physical controller. Inventory remains non-mutating; opening a settings connection or starting heartbeat is a separate user action.

**Dependency baseline (I):** pin `windows = "=0.61.3"`, default `std` enabled; add only features listed per backend. Pin `windows-core = "=0.61.2"` where directly using implementation macros. `windows` transitively uses `windows-future 0.2.1`, whose `IAsyncOperation::get()` supports blocking workers; no Tokio dependency needed. These are design pins, not a claim of a completed GNU-target build. Sources: [windows manifest/features](https://docs.rs/crate/windows/0.61.3/source/Cargo.toml), [windows-core implementation macro](https://docs.rs/windows-core/0.61.2/windows_core/attr.implement.html), [blocking get](https://docs.rs/windows-future/0.2.1/windows_future/struct.IAsyncOperation.html#method.get).

## 1. Receiver HID: settings, ordinary pad state, physical paddles

### APIs and collection selection

**I:** use `windows`, not WinRT `Windows.Devices.HumanInterfaceDevice.HidDevice`. Win32 exposes descriptor-derived lengths and cancellable overlapped I/O directly, needs no package identity/HID capability declaration, and fits the existing blocking worker. WinRT would add device-access/manifest/async-event policy without improving this fixed-report protocol. The original app's choice is evidence of its UWP environment, not a requirement for our desktop port.

Features: `Win32_Foundation`, `Win32_Devices_HumanInterfaceDevice`, `Win32_Devices_DeviceAndDriverInstallation`, `Win32_Devices_Properties`, `Win32_Storage_FileSystem`, `Win32_System_IO`, `Win32_System_Threading`, `Win32_Security`. Optional XInput adds `Win32_UI_Input_XboxController`.

1. `HidD_GetHidGuid` → `SetupDiGetClassDevsW(..., DIGCF_PRESENT | DIGCF_DEVICEINTERFACE)` → `SetupDiEnumDeviceInterfaces` → two-call `SetupDiGetDeviceInterfaceDetailW`; initialize each structure's `cbSize` using the Windows ABI, not a packed Rust approximation. Retain `SP_DEVINFO_DATA` for instance/container correlation. `SetupDiDestroyDeviceInfoList` releases enumeration state. Equivalent CM enumeration is `CM_Get_Device_Interface_List_SizeW` + `CM_Get_Device_Interface_ListW` with the HID interface GUID and `CM_GET_DEVICE_INTERFACE_LIST_PRESENT`; choose one enumeration implementation, not two divergent discovery paths.
2. Open candidate interface with `CreateFileW` desired access 0, share `FILE_SHARE_READ | FILE_SHARE_WRITE`, `OPEN_EXISTING`. Query `HidD_GetAttributes` for **VID `2dc8`, PID `3024`**. Call `HidD_GetPreparsedData` → `HidP_GetCaps` → `HidD_FreePreparsedData`; require **UsagePage `ff00`, Usage `0001`**. A VID/PID string match alone is insufficient.
3. Record `SetupDiGetDeviceInstanceIdW`, `SetupDiGetDevicePropertyW(DEVPKEY_Device_ContainerId)`, and parent ancestry through `CM_Get_Parent` / `CM_Get_Device_IDW`. Reopen only selected vendor collection with `GENERIC_READ | GENERIC_WRITE`, shared read/write, `OPEN_EXISTING | FILE_FLAG_OVERLAPPED` semantics (`OPEN_EXISTING` is creation disposition; `FILE_FLAG_OVERLAPPED` is flags). Do not open the mouse or gamepad collection for configuration.
4. `ReadFile`/`WriteFile` with distinct persistent `OVERLAPPED` structures/events (`CreateEventW`), `ERROR_IO_PENDING`, `WaitForMultipleObjects` including stop event, and `GetOverlappedResult`. Preserve buffers/OVERLAPPED until completion. `CancelIoEx` followed by completion reaping precedes `CloseHandle`; cancellation is not permission to free an in-flight buffer. `CM_Register_Notification`/`CM_Unregister_Notification` may drive rediscovery; callbacks only enqueue arrival/removal.

**D/O: report length is 32, not an automatically added 33.** `HIDP_CAPS::{InputReportByteLength,OutputReportByteLength}` already **include report ID**. The observed descriptor has 31 data bytes plus ID `81`; original serializer `0x180c4b550` allocates `0x20`, sets array[0]=`81`, then copies at most `0x1f` bytes (IR `UWPAdvance.008.c`, evidence `ev_d2692710de786f469fdb89e7ca96057ca2a9c1e36c209d759ab7df48f991566f`). Our existing `[u8;32]` already contains the ID. Never prepend `00` or a second `81`. Allocate/read the exact input caps length, write the output caps length, with `81` at byte 0. Expected caps are 32/32; record actual values first. If caps differ, establish descriptor/report-ID-specific layout before sending; do not guess between 32 and 33 by spraying writes. Caps can describe a maximum across IDs, not necessarily this ID's logical content.

**O:** original selector `0x180cb1580` passes `(ff00,1,2dc8,3024)` (`UWPAdvance.009.c`, evidence `ev_a2e4840518558b197fcceb1990abcf9c6887bb5d5fb99228473bd2eea8351591`). `original/AppxManifest.xml:28–40` declares `humaninterfacedevice` for exactly this usage. **I/U:** standard-user vendor access is expected under the normal HID device DACL; this is neither a keyboard/mouse exclusive collection nor an administrator-only WinUSB takeover. Confirm actual `CreateFileW` as an unelevated user; report `ERROR_ACCESS_DENIED`/sharing conflicts instead of requiring blanket elevation or replacing drivers. Close original Ultimate Software before exclusive protocol ownership.

The receiver's gamepad is a **separate function/interface**, not `FF00:1`. **L:** USB interface 0 is xpad-compatible, interface 4 mouse, interface 5 vendor HID; interfaces 1–3 audio. **D/I:** Windows normally exposes XUSB/XInput through its inbox Xbox stack (often xusb22), plus compatibility HID children. Actual Windows service/path names require enumeration; Linux's xpad name is not a Windows driver identifier. Do not replace the gamepad driver with WinUSB or hide the whole composite receiver indiscriminately.

### Input and protocol ownership

**I:** one receiver I/O owner/demultiplexer shares ordinary samples, physical samples, and configuration replies. Serialize settings transactions and writes; pause the single heartbeat schedule throughout profile transactions and restore reporting using existing semantics. Never have competing readers steal acknowledgments. Multiple UI consumers subscribe to the owner, not independent command queues.

- Standard pad source: prefer existing `receiver::pad` over **`81 14`** vendor reports. Same selected device, independent LT/RT, no ambiguous XInput index, and still accessible when only the gamepad collection is cloaked. Decode buttons at 2..3, LT/RT at 4/5, signed sticks at 6/8/10/12. Bytes 22..31 are stale residue, never battery/IMU/paddles.
- Optional test-only source: `XInputGetState(user_index, &XINPUT_STATE)`, indices 0..3, plus `XInputGetCapabilities`. XInput does not expose a PnP path in its state API. Do not equate “first connected index” with this receiver or accidentally select our ViGEm pad. Prefer vendor state unless same-device correlation is established; exclude virtual `get_user_index()`.
- Physical paddles: reuse `receiver::{heartbeat_frame,physical_input,Paddles}`. Send **`81 10 04 55` + 28 zero bytes every 400 ms**, only while Test/mapper needs physical state; no acknowledgment/retry. Heartbeat emits additional **`81 1c 04 00 03 00 ...`** packets, keys LEu32 at 18..21: L4 `00200000`, R4 `40000000`, PL `02000000`, PR `04000000`. Sticks at 22..25, triggers 26/27 belong to this physical packet, not `81 14` residue.
- **L:** physical reports are change-driven. Keep held state until the next physical report; no one-second silence release. Preserve existing D-pad quirk filter: suppress simultaneous PL|PR alias while direction is held. Only vendor physical paddles supplement normal gamepad input; do not double-apply standard buttons from both streams. Disconnect/worker shutdown neutralizes all outputs.

Heartbeat static route: `0x180c4c9c0 → 0x180c4cbd0 → 0x180c4d5f0`, `ev_d8af8df7e5b2e999018e706966432d5dbad6401f998b73125b730ac5ae5525ec`; [spec-test-paddles.md](spec-test-paddles.md) explains recovered Windows behavior. Later live facts in [replacement-plan.md](replacement-plan.md) establish heartbeat/paddles beyond that older spec's unknowns.

**Threading/permissions:** one native worker, no COM apartment needed for Win32 HID; GUI receives messages only. No driver installation, administrator token, MSIX identity, or AppContainer capability required for the Win32 path. Sources: [opening HID collections](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/opening-hid-collections), [caps lengths](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/hidpi/ns-hidpi-_hidp_caps), [HID shared/exclusive access](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/hid-architecture), [XUSB compatibility HID](https://learn.microsoft.com/en-us/windows/win32/xinput/directinput-and-xusb-devices).

## 2. Bluetooth configuration: WinRT GATT

Features: `Foundation`, `Foundation_Collections`, `Devices_Bluetooth`, `Devices_Bluetooth_Advertisement`, `Devices_Bluetooth_GenericAttributeProfile`, `Devices_Enumeration`, `Storage_Streams`, `Win32_System_WinRT`; `windows = =0.61.3`, default `std`. No BlueZ, fixed-CID socket, or manual ATT MTU exchange on Windows.

**Implementation (2026-10-19):** `src/att/windows.rs` implements discovery, GATT configuration and physical-input notifications with unchanged public signatures. `scan`, `backup` and `ble-write` use the native Windows backend; `Connection` shares its profile transaction methods, packet builders, acknowledgment validation (including commit total 868), CRC-checked read retries and report restoration with Linux. Notifications enter a channel as application values, without an invented ATT prefix. Discovery retains address/type across scan responses; `Radio.adapter_address` and `adapter_address_type` are empty on Windows because the watcher does not identify the receiving adapter. Connection operations poll WinRT async status with timeout/stop checks before `.get()`, request cancellation on expiry, and do not claim cancellation immediately ends OS work. MTU negotiation remains Windows-owned and links below 65 are refused. Bluetooth host mapping remains explicitly unsupported until its Windows input/output backend exists. No Windows Bluetooth hardware execution is claimed.

### Exact connection sequence

1. On explicit Connect Bluetooth, create `BluetoothLEAdvertisementWatcher::new()`, `SetScanningMode(BluetoothLEScanningMode::Active)`, register `Received`/`Stopped` with `TypedEventHandler`, then `Start()`. Match `args.Advertisement()?.LocalName()? == "81HF01"`; aggregate observations by Bluetooth address because name may arrive in scan response. Preserve `BluetoothAddress()` and `BluetoothAddressType()`. Stop after existing bounded discovery window, `Stop()` and remove event tokens. Multiple candidates require explicit selection, not first match. **L:** hold controller front pixel/profile button ~3 s until configuration LEDs blink; close competing mobile app.
2. `BluetoothLEDevice::FromBluetoothAddressAsync(address)?.get()`; for observed public/random address type prefer the exact Rust overload `FromBluetoothAddressWithBluetoothAddressTypeAsync(address, address_type)?.get()`. Advertisement discovery first populates Windows' cache; null/unavailable device is an error, not proof pairing is required.
3. `GattSession::FromDeviceIdAsync(device.BluetoothDeviceId()?)?.get()`, then `SetMaintainConnection(true)`. Observe `SessionStatus`/`SessionStatusChanged`; this property requests continued connection, not synchronous proof of a connected peripheral.
4. Discover with `GetGattServicesForUuidWithCacheModeAsync(uuid, BluetoothCacheMode::Uncached)?.get()`, then each service's `GetCharacteristicsForUuidWithCacheModeAsync(uuid, Uncached)?.get()`. Check result `Status()` and `ProtocolError()`, then discovered list cardinality/properties. Never hardcode handles.

Keep `src/att.rs::SERVICES/TRANSPORTS` preference and packet-CRC selection:

| Service UUID | Characteristic UUID | Packet CRC policy |
|---|---|---|
| `0000ff10-0000-1000-8000-00805f9b34fb` | `0000ff11-0000-1000-8000-00805f9b34fb` | false |
| same FF10 | `0000ff13-0000-1000-8000-00805f9b34fb` | true |
| `00010203-0405-0607-0809-0a0b0c0d1910` | `00010203-0405-0607-0809-0a0b0c0d2b11` | false; verified 3E physical endpoint |

5. Require `Notify` and `WriteWithoutResponse` or `Write` in `CharacteristicProperties()`. Register `ValueChanged` **before** `WriteClientCharacteristicConfigurationDescriptorAsync(Notify)?.get()`. Event callback reads `CharacteristicValue()` via `DataReader::FromBuffer`/`ReadBytes`, copies bounded application value into worker queue, returns immediately. The WinRT buffer already excludes ATT opcode/handle: **do not strip the three ATT bytes that Linux's raw notification wrapper strips**. Application value still includes its own `81 ...` wrapper.
6. `DataWriter::new()` → `WriteBytes(&frame)` → `DetachBuffer()` → `WriteValueWithResultAndOptionAsync(buffer, GattWriteOption::WriteWithoutResponse)?.get()`. Use `WriteWithResponse` only when that discovered characteristic lacks without-response and supports ordinary Write, matching existing ATT behavior. Check `GattWriteResult::Status`/`ProtocolError`. OS write success is not application acknowledgment; existing opcode/offset/count acknowledgment and commit/read-back validation remain mandatory.
7. `protocol::PACKET_SIZE` is **62 bytes**. Require `GattSession::MaxPduSize() >= 65` for native ATT write-without-response (`MTU−3` payload). Observe `MaxPduSizeChanged` during connection establishment; Windows negotiates MTU, app cannot set 250 as Linux does. Do not split one vendor packet into unrelated GATT writes or substitute long-write semantics. Insufficient negotiated MTU → explicit unsupported-link error before profile traffic. Larger MTU does not increase existing vendor chunk size 43.
8. Close: stop issuing work; unsubscribe CCCD with `None` when reachable, remove event handlers, `SetMaintainConnection(false)`, close retained `GattDeviceService`, `GattSession`, `BluetoothLEDevice` (`IClosable` projections expose `Close`). Handle disconnection without claiming cleanup reached an unreachable device.

**Threading:** dedicated worker calls `RoInitialize(RO_INIT_MULTITHREADED)` and eventually `RoUninitialize`; objects/event tokens owned until shutdown. `.get()` is allowed on this blocking MTA worker, never GUI STA or within a callback needed to complete the same operation. WinRT callback threads only enqueue. Serialize GATT work; event queue feeds existing application parser. `.get()` has no application deadline parameter; do not promise instant cancellation of Windows connection/discovery. Where existing stop/deadline contract requires bounded responsiveness, retain async operation, observe `Status`/completion with a worker stop event, request `Cancel` where supported, ignore late results after session cancellation, and release safely. Windows explicitly cannot cancel its underlying BLE connection process; no competing request storm.

**Permissions/pairing:** Windows 11 supports unpaired GATT access; pairing the gaming HID and accessing the separate `81HF01` configuration bearer are different operations. Attempt unpaired configuration first. Pair only if discovered attribute security/access errors establish a requirement; use Windows Settings rather than assuming desktop `DeviceInformationPairing::PairAsync`/consent UI works on arbitrary worker threads. No administrator needed. Full-trust unpackaged Win32 can use these BLE APIs. Packaged/AppContainer builds declare `<DeviceCapability Name="bluetooth" />` and honor Windows privacy policy. **O:** original manifest declares HID but no Bluetooth capability; do not copy that omission into a new BLE-capable package.

Sources: [Microsoft GATT client sequence](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/gatt-client), [Bluetooth desktop/unpaired FAQ](https://learn.microsoft.com/en-us/windows/apps/develop/devices-sensors/bluetooth-dev-faq), [FromBluetoothAddress cache/connection contract](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.bluetoothledevice.frombluetoothaddressasync), [MaxPduSize](https://learn.microsoft.com/en-us/uwp/api/windows.devices.bluetooth.genericattributeprofile.gattsession.maxpdusize), [desktop WinRT restrictions](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/winrt-api-desktop-app-support), [pinned Bluetooth source](https://docs.rs/crate/windows/0.61.3/source/src/Windows/Devices/Bluetooth/mod.rs), [pinned GATT source](https://docs.rs/crate/windows/0.61.3/source/src/Windows/Devices/Bluetooth/GenericAttributeProfile/mod.rs).

Features: `Gaming_Input_Custom`, `Gaming_Input`, `Foundation`, `Foundation_Collections`, `System`, `Devices_Power`, `Win32_System_WinRT`, `Win32_Foundation`, `Win32_Storage_Packaging_Appx` (identity diagnostics), plus direct `windows-core = =0.61.2`. Use `#[windows_core::implement(ICustomGameControllerFactory)]`; **there is no Cargo feature named `implement` in windows 0.61.3**. Implement generated `ICustomGameControllerFactory_Impl` on macro-generated `Factory_Impl`.

**I:** register process-owned factory for recovered GUIDs with `GameControllerFactoryManager::RegisterCustomFactoryForGipInterface(&factory, guid)` early. Both are broad selectors; `CreateGameController(provider)` must filter `IGameControllerProvider::{HardwareVendorId,HardwareProductId}` to `2dc8:202f`, then `cast::<GipGameControllerProvider>()`. Reject unrelated devices with a null factory result per WinRT contract, not a controller error or fake provider. Do not use restricted global device-manager enumeration as a shortcut. Retain factory for process lifetime; public manager has no matching unregister API.

Factory methods: `CreateGameController(Ref<IGameControllerProvider>) -> Result<IInspectable>`, `OnGameControllerAdded(Ref<IGameController>)`, `OnGameControllerRemoved(Ref<IGameController>)`. Controller input interfaces: `IGameControllerInputSink::{OnInputResumed(timestamp),OnInputSuspended(timestamp)}` and `IGipGameControllerInputSink::{OnKeyReceived(timestamp,keyCode,isPressed),OnMessageReceived(timestamp,messageClass,messageId,sequenceId,messageBuffer:&[u8])}`. Suspension/removal must neutralize input/cancel pending work; do not reproduce D4X's trivial success callbacks as host-mapper no-ops.

**Important identity/lifetime obligation:** original D4X is not just a sink-only `#[implement]` object. Factory `0x180004d50 → 0x180004af0` returns an embedded nondelegating `AggregationWrapper` IInspectable; sink interfaces delegate identity/refcount to a controlling unknown. Wrapper QI `0x180002b70` exposes private IID **`06E58977-7684-4DC5-BAD1-CDA52A4AA06D`**; vtable `0x1800086a0` slot 6 is outer setter `0x180002970`. It rejects null/self/late aggregation (`CLASS_E_NOAGGREGATION`), then installs supplied controlling unknown. Nondelegating QI `0x180002d10` exposes input sinks/ID4X, not IGameController. **I:** Windows supplies outer through this hook; invocation itself has not been observed live. Evidence: D4X IR functions above, `ev_8b9eeb346c176a2fc1a905dd8415c84b0b5ddb4553dce8ecb77e46cf3d0608ac` and `ev_6edb4223fa5f0ee84f5fe0951e32222c510f0555ea68721d18f96a533379b39d`.

A faithful experimental Rust implementation therefore needs macro-generated factory **plus an explicit aggregation-compatible COM wrapper**, nondelegating refcount/QI and delegating sink interfaces; macro use alone does not supply that private hook. Alternative public-interface design implements full `IGameController` plus sinks and real property/event forwarding, but is **unproven equivalent**, not a license to fabricate `User`, `Headset`, `IsWireless` or return inert event tokens. `IGameController` methods include `HeadsetConnected`/remove, `HeadsetDisconnected`/remove, `UserChanged`/remove, `Headset`, `IsWireless`, `User`. `TryGetFactoryControllerFromGameController` provides factory-object conversion; it does not manufacture an outer controller. Acceptance must prove QI identity, callbacks, lifetime, and reconnect before transactions. See [factory controller identity contract](https://learn.microsoft.com/en-us/uwp/api/windows.gaming.input.custom.gamecontrollerfactorymanager.trygetfactorycontrollerfromgamecontroller) and [pinned Custom projections](https://docs.rs/crate/windows/0.61.3/source/src/Windows/Gaming/Input/Custom/mod.rs).

### Frame mapping and feature use

**O:** `.winmd` `ID4XDevice.SendMessageId(byte[],uint)`, token `06000024`, slot 14, is called by UWP `0x180c4b340 → 0x1808c6990`. D4X `0x180001ad0` forwards to provider slot 6. Constructor/init `0x180004af0` / `0x180001760` obtain `IGipGameControllerProvider` IID `DBCF1E19-1AF5-45A8-BF02-A0EE50C823FC` and base provider IID `E6D73982-2996-4559-B16C-3E57D46E58D6`. Receive `0x180001800` copies payload and dispatches message ID. WinMD SHA-256 `b4af28b7a0a275d6aff3bf6cff260ec2cbf026827b7f8381f7ba4e409a4dccd3`, MVID `1859daaa-e6d9-475b-b28d-9377824f6658`; evidence index in [spec-gip.md](spec-gip.md).

- Send exactly `GipGameControllerProvider::SendMessage(GipMessageClass::Command, 0x13, &P60)`. `Command` is enum value **0**, not GIP System flag `20`.
- Build **60 application bytes** with `WindowsCommand::gip60_buffer`: channel byte, LE16 opcode, LE16 parameter, LE32 count/total/offset, payload ≤41, zero padding. No HID ID, no outer HID length, no four-byte raw GIP header. Do **not** call Linux `gip::command_frame` or replay usbfs sequence/ACK/fragmentation logic: Windows owns transport sequencing and reassembly.
- `OnMessageReceived` accepts only matching provider and `Command`/message ID **`0x12`** for configuration. Copy buffer once into bounded worker queue; callback slice is borrowed. Feed complete **application payload** to existing `gip::parse_reply`; version uses the live-corrected 17-byte kind-5 header, ordinary acks their existing layout. Physical `04 00 03 ...` is not configuration progress. Do not assume callback `sequenceId` is vendor transaction correlation.
- Calibration travels the **same SendMessage path**: channel 4, opcode `0e` Start / `0f` End, selector 1 sticks / 2 triggers, zero count/total/offset. PC recovery likewise channel 4, opcode `0a`, parameter **1** (`enable_xinput_mode`); reverse PC→Xbox uses receiver opcode `0a`, parameter **0**, not a second driver API. Commands can disconnect before ack: confirm resulting same-device mode/reenumeration, not arbitrary timeout=success.
- **L:** this firmware does not supply vendor physical GIP reports during calibration; Linux uses standard GIP input `20`. On Windows acquire same-controller `Gamepad::FromGameController` / `RawGameController::FromGameController` from added controller identity, use `Gamepad::GetCurrentReading` or `RawGameController::GetCurrentReading` for movement gates. Convert normalized axes/triggers once to existing calibration state-machine contract. Do not assume standard GIP input is delivered as custom message `12`, or wait forever for nonexistent paddle reports.
- Battery: `Gamepad::TryGetBatteryReport` / `RawGameController::TryGetBatteryReport` (`IGameControllerBatteryInfo`), `BatteryReport::{Status,RemainingCapacityInMilliwattHours,FullChargeCapacityInMilliwattHours}`. Nullable report/capacities → unavailable. Percent only when both capacities exist and full >0. No receiver residue-byte battery decoder. Actual 3E Windows result remains **U**; Linux xone four-level battery is not proof Windows supplies percentage. [Battery API](https://learn.microsoft.com/en-us/uwp/api/windows.gaming.input.igamecontrollerbatteryinfo.trygetbatteryreport).

**Threading/permissions:** initialize WinRT MTA on device worker. Factory/sink callbacks can arrive on arbitrary threads; synchronize lifetimes and enqueue work, never block callbacks awaiting vendor replies. One serial transaction worker owns pending requests, not a mutex held across callbacks. Inbox GIP driver remains bound; no Linux-style takeover, usbfs, WinUSB installation, or administrator permission should be presumed necessary for factory registration. [Provider access contract](https://learn.microsoft.com/en-us/uwp/api/windows.gaming.input.custom.igamecontrollerprovider) says direct device-manager enumeration is restricted to Store apps with `xboxAccessoryManagement`; normal access is a custom factory. This does **not** establish a requirement for that restricted capability on our factory path. Original manifest declares no such capability.

### Critical packaging gate and user consequence

**U: custom GIP factory use from an unpackaged desktop exe is not established. Neither “portable works” nor “MSIX is required and fixes it” is justified.** Microsoft documents agile/Both threading and UniversalApiContract v3, but [Custom namespace remarks](https://learn.microsoft.com/en-us/uwp/api/windows.gaming.input.custom) target OEM WinRT component libraries. General WGI desktop support is not proof of this custom provider lifecycle. **O:** original app is packaged and registers `D4XGaming.Devices.D4XDevice` as `windows.activatableClass.inProcessServer`, threading `both` (`AppxManifest.xml:42–48`); this proves original activation arrangement only.

**Required early A/B:** launch the **same binary and implementation** unpackaged and with MSIX/package identity, same device/OS. Record `GetCurrentPackageFullName` (`APPMODEL_ERROR_NO_PACKAGE` vs actual identity), `RoInitialize`/activation HRESULT, both registration HRESULTs, factory callback delivery, provider QI + VID/PID, added/removed/reconnect, COM identity/aggregation, then one non-persistent version request/reply (`13`→`12`). Registration returning S_OK alone is insufficient. Packaging cannot repair a broken Rust COM implementation, missing GIP interface exposure, or wrong driver binding. Do not redistribute original D4X DLL as a fallback without rights.

**User-facing consequence:** receiver **PC mode already covers profile read/save/test**; Bluetooth configuration covers settings without GIP. Windows GIP is not a prerequisite for the editor. Its unique needs here are **calibration and recovering an Xbox-mode receiver back to PC mode**; both work from Linux today. Until gate passes, label those Windows actions unavailable with Linux recovery instructions; do not switch a user's receiver into Xbox mode without an explicitly available recovery route. GIP profile access can follow later, not block HID/BLE settings delivery.

**Untested non-GIP calibration alternative:** Android has BLE Start/End frames on 2B11, documented in [spec-calibration-battery.md §2](spec-calibration-battery.md#2-android-calibration-over-ble). Each value is exactly **62 bytes**, `Z(n)` means n zero bytes:

| Operation | Characteristic value |
|---|---|
| Sticks Start / End | `81 11 04 0e 00 01 00 || Z(55)` / `81 11 04 0f 00 01 00 || Z(55)` |
| Triggers Start / End | `81 11 04 0e 00 02 00 || Z(55)` / `81 11 04 0f 00 02 00 || Z(55)` |

## 4. Host mapper: virtual pad, keyboard/mouse, physical hiding, gyro

Keep `Mapper` platform-independent. Windows adapter converts actual source samples into its established coordinate/event contract and translates resulting `Frame` to outputs. Preserve saved Linux-named mapping identifiers through explicit key/button lookup; never send Linux evdev numeric codes directly as Windows scan codes. Receiver/GIP XInput sticks have Y-up; existing normalized source contract may be Y-down: normalize once with bounded integer arithmetic, including `i16::MIN`. Declare source ranges accurately (u8 BLE/receiver triggers versus native GIP 10-bit or WGI normalized values). Physical paddle input uses `receiver_physical_at`; turbo/stick-mouse need periodic `tick` even while source is idle. `close()` releases owned keys/buttons, neutralizes virtual pad, and stops gyro before detaching source.

### HidHide gamepad isolation and exact device identity

Use **HidHide v1.5.230.0** stable contract; no additional Rust wrapper required. `CreateFileW("\\\\.\\HidHide", GENERIC_READ, ..., OPEN_EXISTING, ...)` + `DeviceIoControl` through `windows` features `Win32_Storage_FileSystem`, `Win32_System_IO`, `Win32_Foundation`, `Win32_Security`; enumeration/Properties features from §1. Driver installation needs administrator/restart; control API is documented usable without elevation. Only one control handle at a time; acquire for short read/modify/write interval and close.

Stable IOCTL encoding: `CTL_CODE(32769, function, METHOD_BUFFERED, FILE_READ_DATA)`:

| Function numbers | Get / set |
|---|---|
| 2048 / 2049 | whitelist |
| 2050 / 2051 | blacklist |
| 2052 / 2053 | active state |
| 2054 / 2055 | whitelist-inverse state |

Lists are UTF-16 `MULTI_SZ`, double-NUL terminated; lengths **bytes**. Active/inverse values are one-byte `BOOLEAN`, not four-byte `BOOL`. SET replaces full list: read/merge/preserve unrelated entries; concurrent multi-IOCTL changes are not atomic. Whitelist contains executable NT image paths (`\Device\HarddiskVolume...`); blacklist contains **PnP instance IDs**, not `\\?\hid#...` interface paths. Obtain own exe via `GetModuleFileNameW`; direct API must convert DOS path to device-form path correctly. Prefer official CLI for initial provisioning rather than inventing path conversion.

CLI: inventory `HidHideCLI.exe --dev-gaming` / `--dev-all`; inspect `--app-list --dev-list --cloak-state --inv-state`; provision `--app-reg "C:\...\ultimate-control.exe"`, normal whitelist `--inv-off`, `--dev-hide "<exact instance ID>"`, `--cloak-on`. Close HidHide GUI first. Unhide only app-owned additions using `--dev-unhide`, remove owned whitelist using `--app-unreg`; `--cloak-off` is documented emergency recovery, not routine destruction of another remapper's global state. Moving portable executable changes whitelist identity; register final absolute location before hiding anything. Stable CLI JSON has `deviceInstancePath` / `baseContainerDeviceInstancePath`; newer documentation's `xusbDeviceInstancePath` must not be assumed present in 1.5.230.

Discover actual 3E Windows paths; no machine-specific path can be supplied from Linux:

- Receiver gamepad: USB interface 0, typically an XUSB-compatible function with `VID_2DC8&PID_3024&MI_00` ancestry plus HID compatibility child; this is an **identity template**, not a captured Windows instance string. Use SetupDi/CM instance/container/parent properties and CLI output. XInput hiding may require corresponding XUSB/base-container node in addition to HID child; scope the exact relevant node and confirm sibling vendor/audio functions survive. Never blindly cloak whole composite parent.
- Receiver mouse: interface 4 ancestry, expected `VID_2DC8&PID_3024&MI_04`, HID usage 1:2. Identify/log actual instance and Raw Input device path, but **do not claim HidHide can hide it**.
- Vendor configuration: usage FF00:1, interface 5; keep outside gamepad blacklist. Bluetooth gaming HID has its own `BTHENUM`/`BTHLEDEVICE`-derived instance topology; never hide Bluetooth adapter or whole configuration bearer.

**Correction:** “XInput cannot read a hidden pad” is true for denied clients, **not a universal statement about our whitelisted exe**. Stable HidHide `OnDeviceFileCreate` forwards whitelisted opens; physical XInput may remain usable from our allowed process, subject to actual routing checks. Prefer receiver vendor `81 14` regardless. Whitelisted `CreateFileW`/`ReadFile` on gamepad HID, or Raw Input (`RegisterRawInputDevices`, usage 1:5/1:4; `GetRawInputData`; `RIDI_PREPARSEDDATA`/`HidP_GetUsages`/`HidP_GetUsageValue`), are other sources. **D:** XUSB compatibility HID combines LT−RT into one axis; that is not a full-fidelity replacement for independent triggers. Use vendor state, working whitelisted XInput, or WGI; do not claim Raw Input reconstructs lost trigger values.

**Hard limitation:** official HidHide FAQ excludes mice/keyboards/touchpads and says it **cannot block Raw Input**. Therefore it cannot guarantee invisibility from every game, and cannot suppress receiver gyro mouse movement on desktop. This is not fixed by adding the mouse's path to blacklist. Sources: [HidHide FAQ](https://docs.nefarius.at/projects/HidHide/FAQ/), [API](https://docs.nefarius.at/projects/HidHide/API-Documentation/), [CLI](https://docs.nefarius.at/projects/HidHide/CLI-Usage/), [stable driver access policy](https://github.com/nefarius/HidHide/blob/v1.5.230.0/HidHide/src/Logic.c), [XUSB trigger limitation](https://learn.microsoft.com/en-us/windows/win32/xinput/directinput-and-xusb-devices).

### Receiver gyro: Raw Input observation versus suppression

**L:** firmware Motion target Mouse emits relative mouse counts on receiver interface 4 (~4 ms Linux report interval); no receiver/GIP raw IMU. Physical R4/L4/PL/PR clutch comes from vendor heartbeat, independent of stored paddle remapping.

### Optional Interception receiver-mouse filter

**I:** Interception can consume matched receiver mouse strokes before desktop delivery, unlike HidHide. **D/U:** original **Interception v1.0.1** ships signed binaries, but upstream documents testing XP–10, not Windows 11/HVCI certification. Signed does not mean accepted under every Windows 11 Secure Boot/Memory Integrity/blocklist policy. Installation: official release's `install-interception.exe /install` from elevated prompt, reboot; `/uninstall` elevated + reboot removes driver. Set predicate for **matched slot only**, not all mice or keyboards. Forward any intentionally passed-through intercepted stroke unchanged. No Raw Input duplicate processing when Interception owns this source. Other physical mice remain unfiltered.

Threading/latency: dedicated wait/receive worker with bounded timeout for shutdown; no GUI/GATT wait inside interception path, no sleep/poll cadence between receipt and forwarding. Kernel→user scheduling/IOCTL→mapped output adds latency and jitter; upstream provides no defensible numeric bound. Timestamp at receipt using monotonic host clock; driver strokes do not expose raw IMU/HID timestamp. Stop disables owned filter and destroys context; crash, unplug/replug and unrelated-mouse usability require live checks before production claims.

**Licenses are separate:** library/source LGPL terms do not turn binary drivers/installers into unrestricted LGPL components. Upstream grants noncommercial binary driver/installer redistribution conditional on communicating solely through library API. Commercial distribution needs upstream commercial license; “Interception API License” adds commercial rights/installer library, full “Interception License” adds driver/installer source. MIT Rust wrapper does not override these restrictions. Keep Interception optional, separately consented; do not bundle it in a general commercial installer without rights.

## 5. Auto profiles: processes in current user/session

`windows = =0.61.3`, features `Win32_Foundation`, `Win32_System_Diagnostics_ToolHelp`, `Win32_System_Threading`, `Win32_Security`; command-line WMI additionally `Win32_System_Com`, `Win32_System_Wmi`, `Win32_System_Ole`, `Win32_System_Variant`. No third-party process/WMI crate required.

**I:** every second on worker, `CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS,0)` → `Process32FirstW`/`Process32NextW`, initialized `PROCESSENTRY32W.dwSize`, then `CloseHandle`. Snapshot includes other users; it is not a privacy filter. Open candidate with `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, false, pid)`; `QueryFullProcessImageNameW(handle,0,...)` returns path, not arguments. Executable basename supplies `Process.exe`, `szExeFile` supplies `comm`. Handle exit/access-denied races by skipping unreadable identity, not elevating or guessing.

Filter to **own logon session and own user SID**: capture own `GetCurrentProcessId`/`ProcessIdToSessionId`, `OpenProcessToken(TOKEN_QUERY)` and `GetTokenInformation(TokenUser)`; compare candidate SID using `EqualSid`. `ProcessIdToSessionId` requires query rights; token `GetTokenInformation(TokenSessionId)` is an alternative when using already obtained queryable tokens. Session equality alone is not user equality. Unknown owner/session is not a match. No `SeDebugPrivilege`, service session 0 scan, or global process-control rights needed.

**Command line:** recommended supported path is local WMI, not remote PEB scraping. Initialize COM MTA, set process COM security once where needed (`CoInitializeSecurity`, coordinate existing initialization), `CoCreateInstance(CLSID_WbemLocator)` → `IWbemLocator::ConnectServer("ROOT\\CIMV2", current-user credentials)` → `CoSetProxyBlanket` → `IWbemServices::ExecQuery("WQL", "SELECT ProcessId, SessionId, CreationDate, CommandLine FROM Win32_Process WHERE SessionId = <own session>", WBEM_FLAG_FORWARD_ONLY | WBEM_FLAG_RETURN_IMMEDIATELY, ...)`. Enumerate `IEnumWbemClassObject::Next` with finite wait, read `IWbemClassObject::Get`; merge only into SID/session-validated candidates and account for PID reuse via process creation time (`GetProcessTimes`/WMI CreationDate). Keep WMI objects on process-watcher thread; unavailable/null command line is unknown, never empty success. Do not log arguments, which may contain secrets.

Alternative `NtQueryInformationProcess(ProcessCommandLineInformation=60)` from `ntdll.dll` returns counted command-line data on current Windows, but this information class is not covered by Microsoft's public stable query contract. Dynamic resolve (`GetProcAddress`), size/status/pointer validation and version/access handling would be required; do not choose hardcoded PEB offsets/`ReadProcessMemory` across x86/x64 as ordinary design. WMI supplies public `Win32_Process.CommandLine`; `QueryFullProcessImageNameW` does not.

**Behavior decision:** exact case-insensitive exe-name matching (`game.exe`) is acceptable/recommended for ordinary Windows rules and works without argument access. It is **not equivalent** to existing case-insensitive command-line substring matching; preserve that using WMI where readable and expose “command line unavailable” for affected rules instead of silently narrowing all rules to basenames. Keep first rule wins, default fallback, one-second polling, existing two-second debounce, auto off at app start. Running-process selection is not foreground-window selection. Watcher stays independent of minimized/hidden GUI and GATT latency; emits requested profile changes to mapper owner, which releases outputs before restart.

Permissions/package: normal-user portable/full-trust exe; no package capability/admin. Protected/elevated/other-user process metadata can be unavailable; report bounded limitations, not a reason to request debug privilege. Sources: [Toolhelp snapshot](https://learn.microsoft.com/en-us/windows/win32/api/tlhelp32/nf-tlhelp32-createtoolhelp32snapshot), [image path](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew), [session rights](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-processidtosessionid), [token information](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-gettokeninformation), [WMI process properties](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-process), [WMI connection](https://learn.microsoft.com/en-us/windows/win32/wmisdk/creating-a-connection-to-a-wmi-namespace), [native query stability warning](https://learn.microsoft.com/en-us/windows/win32/procthread/zwqueryinformationprocess).
